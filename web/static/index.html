ESP32 sensor node

What's on the board, and how it's wired

An ESP32-S3 reads two analog TDS probes and a temperature probe about once a second, and prints one line per reading over USB. A flow meter can be added later; the software already works with or without it.

From probe to diagnosis

  1. 1
    Read the probes

    The ESP32 takes 30 ADC samples per probe, drops the highest and lowest, and averages the rest into a voltage.

  2. 2
    Send one line per second

    Over USB at 115200 baud: 1.214,0.144,24.81 (Sensor 1 V, Sensor 2 V, °C). With a flow meter, a fourth value is added: 1.214,0.144,24.81,1.85.

  3. 3
    Convert on the laptop

    The Python logger turns voltage into ppm using temperature and each probe's K-value. Calibration lives in software, so you never need to reflash to recalibrate.

  4. 4
    Diagnose and log

    Each reading is saved to data/esp32_live_log.csv and checked by the model; the result is printed live.

Set it up in 5 steps

  1. 1. Wire it as in the table above. Share one GND between all parts.
  2. 2. Install libraries in Arduino IDE: OneWire and DallasTemperature. Board: ESP32S3 Dev Module.
  3. 3. Flash firmware/esp32_sensor_node.ino. Leave FLOW_SENSOR_FITTED false until a flow meter is connected.
  4. 4. Check Serial Monitor at 115200 baud. You should see lines like 1.214,0.144,24.81, then close Serial Monitor so the port is free.
  5. 5. Start the logger: 
    pip install pyserial
python data/data_logging_esp32.py --port /dev/cu.usbserial-XXXX \
  --sample-type "Normal water" --k-in 1.0 --k-out 1.0

    On Windows the port looks like COM3.

Calibrating a TDS probe

  1. Dip the probe in a standard solution of known TDS (for example a 342 ppm calibration buffer) at room temperature.
  2. Read the ppm shown with K = 1.0 (Live Check → My sensor).
  3. Calculate K = known ppm ÷ measured ppm. Example: 342 ÷ 320 = 1.069.
  4. Use that K in the dashboard, Batch Lab, or the logger's --k-in / --k-out.

Your current readings use K = 1.0 (uncalibrated), so their ppm values are approximate.

Tips & troubleshooting

  • Keep the two probes in separate water. Two analog TDS probes in the same container can interfere with each other and skew both readings.
  • Sensor 1 doesn't change between samples? Check it is really in the sample, and that the probe is clean and fully submerged.
  • Voltage near 2.3 V or higher means very high TDS or a wiring problem.
  • Temperature stuck at 25.00 °C usually means the DS18B20 or its pull-up resistor is disconnected.
  • No lines in the logger? Close Arduino Serial Monitor first; only one program can use the port.
ML methodology

How Aqua-Swachh decides

Physics first, then a small machine-learning model, then hard safety rules. Each step is explained below in plain language, with the actual numbers from the trained models.

1. Read

Probe voltage + temperature (+ flow)

2. Convert

Voltage → ppm at 25 °C

3. Physics

Salt rejection and other features

4. Pick model

With flow or TDS-only

5. Classify

Random Forest votes

6. Safety check

Hard rules can override

Step 2 · Voltage to ppm

The probe gives a voltage. Warmer water conducts better, so the voltage is first corrected to 25 °C, then converted with the probe's reference curve:

V₂₅ = V ÷ (1 + 0.02 × (T − 25))
TDS = (133.42·V₂₅³ − 255.86·V₂₅² + 857.39·V₂₅) × 0.5 × K

Example from your data: 1.214 V at 24.81 °C → 453.2 ppm. That's why "Water cooler water" shows lower feed ppm than "Normal water", even though Sensor 1 read the same voltage: the water was ~8 °C warmer.

Steps 4–5 · Two models, chosen automatically

Both are Random Forests (40 trees, depth ≤ 6) trained on the same 1,200 synthetic rows and tested on 300 unseen rows. If a reading has a flow value, the full model is used; if not, the TDS-only model is used.

What the three results mean

Normal

Salt rejection above ~88% (training data: 90–97%) and healthy flow (1.45–2.4 L/min). Nothing to do.

Monitor

Rejection 74–87% and/or flow 1.0–1.45 L/min: early scaling or fouling. Still working; plan a service soon.

Service required

Rejection below ~70% (membrane damage) or flow below ~0.95 L/min (clogged pre-filter). Service now.

Step 6 · Safety rules (always win)

A model can be wrong, so these fixed rules run after it. If any is true, the result becomes Service required, whatever the model said:

  • Output TDS ≥ 250 ppm
  • Salt rejection < 55%
  • Flow < 0.40 L/min (only when flow is measured)

When a rule overrides the model, Live Check shows both what the model said and which rule fired.

Honest limitations

  • Trained on synthetic data. The 100% / 95% scores are on generated data with clean class boundaries. Real-world accuracy will be lower until the model is trained on labelled real readings.
  • Probes not yet calibrated (K = 1.0), so ppm values are approximate. Your samples sit at 86–87% rejection, just under the 88% line, so calibration could change the result.
  • No flow meter yet. Without flow, a clogged pre-filter can't be detected.
  • TDS isn't everything. Low TDS doesn't prove water is safe to drink (bacteria, heavy metals and so on aren't measured).
  • Confidence moves in steps. It's a vote share from 40 trees, so similar readings often show the same number.

Getting real labels (next step)

Labels must come from the known physical state of a cartridge, never from the TDS rules themselves (that would be circular):

  • Normal: readings from a new, flushed RO cartridge.
  • Monitor: cartridges that have treated ~50–75% of their rated volume.
  • Service required: cartridges at end of life, or deliberately fouled on the bench.

Log those with the ESP32, add a filter_status column, and retrain with python -m model.train. We predict a condition class instead of "days left" because estimating remaining life needs months of field data.
